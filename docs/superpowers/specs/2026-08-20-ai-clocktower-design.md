# AI 自主游玩《血染钟楼》设计

日期：2026-08-20

状态：已完成会话评审，等待书面规格复核

## 1. 项目目标

本项目是一个本地运行的 AI 自治《血染钟楼》观战器。人类只旁观，不扮演玩家、说书人或裁判，也不能在游戏运行中修改状态。

首版目标是让 AI 完整游玩一局《暗流涌动》（Trouble Brewing），并满足以下要求：

- 规则由程序严格执行，LLM 只负责推理、欺骗、交流和选择行动。
- 每名玩家拥有隔离的可见事件、模型上下文和笔记。
- 白天讨论采用事件驱动的有限自主调度，不按固定座位机械轮流发言。
- 人类可在单窗口 AI 对话界面中查看正文、模型返回的原始推理字段、工具调用、规则裁决和检查点。
- 游戏历史保存为单个可打开的 JSONL 文件。
- 同一时间只运行一局，不建设批量实验、长期统计或多局管理能力。

项目是一次娱乐性实现。设计遵循最小充分原则，不引入数据库、消息队列、微服务、通用工作流、多供应商插件系统或检查点恢复。

## 2. 首版范围

### 2.1 包含

- 《暗流涌动》官方剧本。
- 一局游戏从设置、首夜、白天、提名投票、后续夜晚到胜负结束的完整生命周期。
- 公开讨论和有界双人私聊。
- 事件驱动候选筛选、短调用响应探测和有限行动预算。
- 确定性说书人策略。
- OpenAI 兼容 Chat Completions 模型接口。
- 全局普通模型、全局短调用模型、玩家普通模型和玩家短调用模型。
- FastAPI 后端、React/Vite 前端和 SSE 实时观战。
- 单个 JSONL 历史文件及笔记变更检查点。
- 停止和继续游戏推进。

### 2.2 不包含

- 其他官方剧本、自定义剧本、旅行者或传奇角色扩展。
- 多局并发、批量实验、跨局统计、排行榜或费用分析面板。
- LLM 说书人。
- 多人私聊或多个场景真正并发。
- 多供应商原生 SDK、供应商插件市场或自动跨模型切换。
- 数据库、消息队列、后台任务系统或微服务。
- 检查点恢复、回滚或从检查点继续运行。
- 人类加入游戏、手动裁决或注入游戏事件。
- 桌面应用壳、安装程序或远程部署。

## 3. 运行形态

开发期使用 Python/FastAPI 后端与 React/Vite 开发服务器。生产构建后，FastAPI 直接提供前端静态资源、HTTP 接口和 SSE 事件流，实际使用只需启动一个 Python 进程并在本地浏览器中打开页面。

服务器根据 `config.toml` 自动开始一局游戏。同一进程内只允许一个活动游戏。游戏结束后如需开始新局，重新启动进程。

运行控制只有：

- `停止`：当前模型响应或规则原子操作完成后，在下一个安全调度边界停止推进。
- `继续`：从安全调度边界恢复推进。

停止不取消正在进行的网络请求，也不允许留下半条工具调用或只完成一半的状态变化。

## 4. 总体架构

FastAPI 单进程包含以下模块：

- **游戏编排器**：持有唯一活动游戏，推进昼夜与场景，处理停止和继续。
- **规则引擎**：校验行动、应用角色能力、结算提名投票、死亡和胜负。
- **讨论调度器**：筛选响应候选、执行短探测、分配公开讨论与私聊行动机会。
- **玩家代理**：维护每名玩家的授权事件游标、上下文、笔记和模型续接状态。
- **模型适配器**：调用 OpenAI 兼容端点，解析原始推理、工具调用和正文片段。
- **确定性说书人策略**：从规则引擎给出的合法选项中选择一个结果。
- **历史写入器**：按顺序追加 JSONL 记录并创建检查点。
- **SSE 广播器**：向观战器实时推送上帝视角事件。

模块不直接更新 UI，也不各自写历史文件。模块只产生经过 Pydantic 校验的事件；唯一事件流驱动内存状态投影、历史写入和 SSE 广播。

典型行动数据流为：

```text
调度器选择玩家
→ 玩家代理调用模型
→ 模型提交结构化工具意图
→ 规则引擎裁决
→ 产生事实事件
→ 更新内存状态
→ 追加历史文件
→ SSE 推送观战器
```

## 5. 核心状态与事件

### 5.1 GameState

`GameState` 仅存在于 Python 进程内，保存当前一局的可运行状态：

- 当前天数与阶段。
- 玩家座位、真实角色、认知角色、阵营、生死和死者票。
- 角色能力和提醒标记对应的临时状态。
- 当前公开讨论或双人私聊。
- 待处理事件、提名状态、当日最高票和行动预算。
- 每名玩家的笔记、授权事件游标与普通模型续接句柄。
- 停止状态与随机数生成器状态。

浏览器不能直接修改 `GameState`。

### 5.2 EventRecord

所有已经发生的事实统一写为带递增序号的事件：

```json
{
  "seq": 137,
  "time": "2026-08-20T21:14:02.315+08:00",
  "phase": "day.discussion",
  "type": "player.public_message",
  "actor": "alice",
  "audience": { "kind": "public" },
  "payload": {}
}
```

事件排序只依赖 `seq`，时间用于显示。

`audience` 决定玩家能否读取事件：

- `public`：所有玩家可见。
- `players`：仅指定玩家集合可见。
- `player`：仅单个玩家可见。
- `observer`：仅规则引擎与上帝视角可见。

玩家上下文只能从授权事件构建。观战器读取全部事件，但观战数据通道不会成为玩家模型输入。

### 5.3 模型输出片段

模型输出使用 `call_id` 和 `segment_index` 保留原始顺序：

```json
{
  "type": "model.output_segment",
  "payload": {
    "call_id": "call-42",
    "player_id": "alice",
    "call_purpose": "formal_action",
    "segment_index": 0,
    "kind": "reasoning",
    "source_field": "reasoning_content",
    "text": "模型返回的原始文本"
  }
}
```

片段类型为 `reasoning`、`tool_call`、`tool_result`、`final_message` 或 `provider_metadata`。推理文本不总结、不改写；前端只进行安全转义。

### 5.4 CheckpointRecord

每次 `update_notebook` 成功后，顺序固定为：

```text
notebook_updated
→ 更新内存状态
→ checkpoint
→ 继续调度
```

检查点直接写入同一 JSONL 文件，包含：

- 触发检查点的玩家和事件序号。
- 当时的天数、阶段和活动场景。
- 所有玩家的完整笔记。
- 玩家真实身份、生死和上帝视角角色状态。
- 最新事件序号。

检查点不复制此前完整事件列表，也不保存未完成网络请求、模型连接等运行时对象。检查点只用于复盘查看，不能恢复运行。

## 6. 历史文件

每局生成一个追加式 JSONL 文件，基本顺序如下：

```text
game_header
event
event
notebook_updated
checkpoint
event
...
game_ended
```

`game_header` 保存：

- 历史 Schema 版本。
- 规则和剧本版本。
- 随机种子。
- 去除 API Key 后的模型配置快照。
- 玩家座位与显示名称。

历史文件写入失败或检查点写入失败时立即停止游戏，防止继续产生未审计状态。

## 7. 规则引擎与说书人边界

### 7.1 规则引擎职责

规则引擎是唯一可以改变真实游戏状态的模块，负责：

- 角色配置、座位与初始信息。
- 首夜和后续夜晚行动顺序。
- 醉酒、中毒、保护、注册、死亡和角色能力结算。
- 提名资格、投票、死者票、处决和每日限制。
- 角色即时效果及胜负判定。
- 为玩家生成权限正确的观察结果。

角色规则以官方角色 Almanac 的 “How to Run” 为实现依据。官方资料入口：

- [Trouble Brewing](https://bloodontheclocktower.com/pages/trouble-brewing)
- [Glossary](https://wiki.bloodontheclocktower.com/Glossary)
- [Rules Explanation](https://wiki.bloodontheclocktower.com/Rules_Explanation)

### 7.2 确定性说书人策略

规则存在多个合法结果时，规则引擎发出带合法选项的选择请求。说书人策略只能从合法选项中选择，不能直接修改 `GameState`。

首版策略：

- 不调用 LLM。
- 相同状态和随机种子产生相同选择。
- 允许少量《暗流涌动》专用启发式。
- 记录全部合法选项、最终选择和策略理由代码。
- 不读取玩家推理文本，不根据隐藏思维“读心”。

## 8. 玩家工具

玩家只能通过结构化工具提交意图：

```text
speak_public(text)
request_private_chat(target_player)
respond_private_chat(request_id, accept)
speak_private(chat_id, text)
leave_private_chat(chat_id)
nominate(target_player, accusation)
cast_vote(nomination_id, vote)
use_ability(action, targets)
update_notebook(patch)
yield_action(reason)
```

玩家没有读取全局游戏状态、其他玩家笔记、真实身份或说书人选择的工具。

一次正式行动最多接受一个对外游戏行动；笔记更新不计作对外行动。默认最多四轮工具往返。非法行动允许修正一次；再次非法时，可选行动转为 `yield_action`，必要行动停止游戏。

短调用响应探测不是游戏工具，只返回固定结构：

```json
{
  "decision": "respond | defer | silent",
  "urgency": 0,
  "action_type": "speak | private_chat | nominate | yield"
}
```

## 9. 玩家上下文与笔记

每名玩家拥有独立上下文，包含：

- 自己的身份、阵营和能力说明。
- 自己有权看到的新事件。
- 自己的普通模型续接句柄。
- 自己的笔记。
- 当前场景与可用工具。
- 已读取事件序号。

系统不复制完整全局历史。每次调用前按玩家事件游标筛选新增授权事件。

玩家笔记只包含两个部分：

```json
{
  "notes": "玩家自由维护的 Markdown 文本",
  "attention": {
    "players": [],
    "pending_actions": [],
    "watch_triggers": []
  }
}
```

`notes` 保存角色声明、怀疑、私聊内容和计划。`attention` 只承载调度需要的重点玩家、待办行动和公开触发条件。不建立概率表、知识图谱或复杂信念系统。

## 10. 模型配置与调用

### 10.1 配置层级

`config.toml` 支持四层模型设置：

- 全局普通模型。
- 全局短调用模型。
- 玩家普通模型。
- 玩家短调用模型。

解析顺序为：

```text
普通调用：player.model → models.global

短调用：
player.short_model
→ models.global_short
→ player.model
→ models.global
```

每次调用记录实际模型、配置来源和回退过程。API Key 只通过配置指定的环境变量读取，不写入历史文件。

### 10.2 OpenAI 兼容适配器

首版只支持 OpenAI 兼容 Chat Completions 接口。适配器直接解析 HTTP/SSE 数据，以保留兼容端点返回的非标准字段。

配置提供推理字段候选名，例如：

```toml
reasoning_fields = ["reasoning_content", "thinking"]
```

适配器按实际返回顺序生成 `reasoning`、`tool_call`、`tool_result` 和 `final_message` 片段。若多个推理字段同时存在，分别保存，不合并。

流式 Delta 实时通过 SSE 发给观战器；片段完成后再一次性追加到历史文件。中途失败的片段标记为 `incomplete`。

### 10.3 普通调用

普通调用用于正式推理、公开或私聊发言、提名投票和夜间玩家选择。流程为：

```text
解析模型配置
→ 读取新增授权事件
→ 注入身份、能力、笔记和场景
→ 提供当前允许的工具
→ 调用模型
→ 记录全部原始片段和工具过程
→ 更新事件游标和原生续接句柄
```

### 10.4 短调用

短调用用于响应意愿和结束日探测，只读取最新触发事件、少量相关上下文、玩家笔记和行动预算。短调用不使用游戏工具、不修改笔记，也不写入普通模型续接链。

短调用的原始推理仍写入上帝视角历史，并标记调用用途。

### 10.5 推理续接

原始推理展示与模型上下文续接相互独立：

- 模型返回的 `reasoning_content`、`thinking` 等字段原样保存和展示。
- 同一工具循环中按供应商协议传回必要的 assistant/tool 数据。
- 只有供应商原生支持时才续接推理状态。
- 不把原始推理文本手工拼接进不兼容模型的后续输入。
- 长期连续性由玩家笔记和授权事件保证。

## 11. 事件驱动讨论调度

### 11.1 确定性候选筛选

公开事件先以结构化字段筛选候选，包括：

- 事件当事人或被点名玩家。
- 正在与当事人对话的玩家。
- 笔记中触发 `watch_triggers` 的玩家。
- 有相关待执行计划的玩家。
- 长时间未获得行动机会的玩家。
- 当前阶段允许执行相应行动的玩家。

中央调度器不能读取或解释玩家秘密笔记正文。玩家私有相关性只能通过其结构化 `attention` 元数据或本地短调用体现。

### 11.2 基础分数

基础分由可解释特征组成，例如直接目标、公开点名、触发器匹配、待执行计划、公平度、连续发言冷却、重复内容惩罚和个人预算。权重配置化，且每次评分记录分项理由。

### 11.3 前两名短探测

基础分排名最高的两名玩家执行短调用，返回 `respond`、`defer` 或 `silent` 及有限的紧迫度修正。短调用最多在固定范围内调整基础分，不能完全控制调度结果。

最终从超过阈值的候选中进行带随机种子的加权选择。高分玩家更可能行动，但不永远机械地选择最高分。

### 11.4 讨论结束

连续若干次无有效候选或玩家均选择沉默时进入安静窗口。场景同时受以下硬限制保护：

- 单名玩家连续行动冷却。
- 单名玩家每场景行动上限。
- 私聊行动上限。
- 白天总行动上限。

达到白天硬上限后仍必须执行结束日提名探测，不能直接跳过提名。

## 12. 双人私聊

首版只支持双人私聊，但会话参与者字段使用列表，以便未来扩展而不改变历史格式。

流程为：

1. 玩家调用 `request_private_chat`。
2. 受邀玩家用短调用接受、拒绝或延后。
3. 接受后创建只有两名参与者可见的子场景。
4. 子场景继续使用事件驱动候选与行动预算。
5. 任一方持续无新信息或达到行动上限后结束。
6. 双方分别更新自己的笔记，不生成共享总结。
7. 公开事件只记录双方曾经私聊，不公开内容。

同一时刻只运行一个场景；首版不模拟多个私聊并发。

## 13. 昼夜与提名状态机

### 13.1 夜晚

- 按《暗流涌动》夜序逐项推进。
- 需要玩家选择时使用普通模型。
- 被动接收信息不额外调用模型。
- 醉酒或中毒玩家按自身认知行动，规则引擎决定实际效果与信息。
- 夜间不允许玩家讨论或私聊。
- 所有角色处理后统一结算黎明死亡。

### 13.2 白天

白天由公开讨论、双人私聊和提名流程交替组成。任何公开或私密行动都产生事件并重新触发候选评分。

### 13.3 提名与投票

合法提名暂时中断普通讨论：

1. 提名者提交目标和指控。
2. 被提名者获得一次正式回应。
3. 规则引擎按官方座次顺序请求投票。
4. 投票使用玩家普通模型。
5. 后投票者能看到此前已公开举票的玩家。
6. 更新当日当前“即将被执行者”。
7. 无即时执行效果时返回公开讨论。

规则引擎执行官方限制：只有存活玩家能提名；玩家每日最多提名一次、每日最多被提名一次；活人可多次投票；死人整局只剩一票；候选票数需达到存活人数一半且严格高于此前最高票；平票无人执行。

角色能力造成即时执行时，白天立即结束。

### 13.4 白天结束

讨论与私聊进入安静窗口后，对所有仍有提名资格的存活玩家执行结束日短探测：

- 有玩家希望提名时，选择一名玩家进入提名流程。
- 无人希望提名时，结束提名并结算今日执行。
- 无人达到条件时记录无人执行。

执行或无人执行后检查所有胜负条件，未结束则进入下一夜。

## 14. 错误处理

### 14.1 短调用失败

自动重试一次。仍失败时忽略意愿修正，使用确定性基础分继续调度。

### 14.2 可选正式行动失败

自动重试一次。仍失败时记录错误并将本次行动视为 `yield_action`。

### 14.3 必要选择失败

自动重试一次。仍失败时在安全点停止游戏，不替玩家随机选择。修正网络、密钥或模型配置后点击继续；后端重新读取模型连接配置，记录 `model_config_reloaded`，再执行必要选择。

### 14.4 非法工具调用

返回仅该玩家可见的 `tool_error` 并允许修正一次。再次非法时，可选行动放弃，必要行动停止游戏。非法参数仍写入上帝视角历史。

### 14.5 观战器断开

游戏继续运行。浏览器重连时携带最后收到的事件序号，后端补发缺失事件后恢复实时推送。

### 14.6 历史写入失败

立即停止游戏。只有历史和检查点重新可写后才能继续。

## 15. 观战器交互

### 15.1 实时信息流

页面主体为一条纵向 AI 对话信息流，按发生顺序显示：

- 玩家原始推理。
- 工具调用和工具结果。
- 公开或私聊正文。
- 规则引擎和调度器事件。
- 检查点标记。

不同玩家以显示名称、头像、固定配色、真实角色和阵营区分。旁观者可以显示全部过程，或仅过滤正文、原始推理、工具与规则事件。

原始推理默认允许折叠。模型实际返回的字段名和原文同时显示。旁观者向上滚动时不自动跳到底部，只显示返回最新事件的提示。

### 15.2 运行控制

页面只提供当前状态对应的停止或继续操作。不提供倍速、阶段跳转、单步执行、状态修改或人工裁决。

### 15.3 历史会话

“打开历史记录”使用浏览器文件选择器读取 JSONL 文件，在同一页面切换到历史模式：

- 不上传远程服务器。
- 不导入数据库。
- 复用实时信息流组件。
- 可以完整滚动查看。
- 不显示停止或继续。
- 返回实时模式后补齐离开期间的事件。

### 15.4 检查点查看

检查点在信息流中显示为书签。点击后在同一窗口右侧打开详情，包含：

- 天数、阶段和事件序号。
- 所有玩家的真实身份、生死与角色状态。
- 玩家选择器及所选玩家当时的完整笔记。
- 当前场景与触发检查点的笔记更新事件。
- 定位到对应事件的操作。

详情只读，没有恢复、回滚、编辑或导出能力。

## 16. 验证策略

### 16.1 规则测试

- 每个《暗流涌动》角色具有独立单元测试。
- 覆盖清醒、醉酒、中毒、死亡、注册异常及关键角色交互。
- 覆盖角色配置人数、夜序、提名限制、死者票、平票、立即执行和胜负条件。
- 规则测试使用固定种子，不调用真实模型。

### 16.2 信息隔离测试

- 公共事件投递给所有玩家。
- 私聊只投递给参与者。
- 私密夜间信息只投递给目标玩家。
- 观战事件、真实身份和其他玩家推理永不进入玩家上下文。
- 玩家无法通过工具读取全局状态。

### 16.3 调度测试

- 候选基础分逐项可解释。
- 前两名短探测和回退路径正确。
- 固定种子下候选选择可复现。
- 冷却、安静窗口和行动硬上限能够终止讨论与私聊。
- 白天硬上限后仍执行结束日提名探测。

### 16.4 模型适配测试

- 解析 `reasoning_content`、`thinking`、正文和工具调用的各种顺序。
- 流式分块不改变最终文本。
- 同时出现多个推理字段时分别保存。
- 中断流生成 `incomplete` 片段。
- 四层模型配置与回退顺序正确。
- 短调用不污染普通模型续接链。

### 16.5 历史与检查点测试

- 事件序号严格递增。
- 笔记更新后紧接检查点。
- 历史文件可逐行重建完整观战信息流。
- 检查点能展示对应时间的全部玩家笔记和状态。
- 历史或检查点写入失败会停止游戏。

### 16.6 前端测试

- 不同玩家、推理、工具、规则和私聊内容清晰区分。
- 原始推理可以展开、折叠和过滤。
- 实时断线重连后不会重复或丢失事件。
- 历史文件可以打开并滚动查看。
- 检查点详情只读且能定位事件。
- 页面只提供停止与继续两种进程控制。

### 16.7 完整验收

首版完成的最低验收条件：

1. 使用固定配置启动本地服务并自动开始一局。
2. 至少五名 AI 玩家在无人干预下完成一局《暗流涌动》。
3. 游戏包含夜间能力、公开讨论、一次双人私聊、提名、投票、执行或无人执行以及最终胜负。
4. 观战器按顺序展示原始推理、工具过程、正文和规则事件。
5. 每次笔记更新都产生可查看检查点。
6. 游戏结束后，关闭服务并重新打开生成的 JSONL 文件，仍能完整滚动复盘。
7. 自动化测试证明任何玩家都未收到无权查看的信息。

## 17. 设计原则总结

- LLM 提出意图，规则引擎决定事实。
- 说书人策略只解决合法结果中的裁量。
- 玩家上下文按事件权限隔离。
- 原始模型推理用于上帝视角观战，不等同于长期记忆。
- 长期记忆由玩家自己的笔记承担。
- 所有可观察过程归入一条顺序事件流和一个历史文件。
- 单局娱乐目标优先，非必要不增加实体。
